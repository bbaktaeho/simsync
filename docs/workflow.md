2. 계획 검토
3. 구현
4. 구현이 목적에 부합하는지 검토
5. 잠재적 버그, 크리티컬 이슈, 보안 문제 검토
6. 개선 사항에 문제가 없는지 검토
7. 기존 코드와 통합/재사용 가능 여부 검토
8. 사이드 이펙트 검토
9. 전체 변경 사항 재검토

## 1. 계획 수립

요구사항을 분석하고 구현 방향을 정한다.
- 어떤 문제를 해결하는지 명확히 한다
- 영향받는 파일과 모듈을 파악한다
- 구현 범위를 정의한다
- 계획은 docs/plan/{순번}-{날짜}-{계획서명}/plan.md 에 작성한다
  - plan.md는 계획서의 핵심 요약이며, 상세 내용은 같은 디렉토리의 개별 문서를 참고하라고 가이드한다
  - 상세 문서는 {순번}-{상세내용}.md 형식으로 필요한 만큼 작성한다
  - 예시 구조:
    ```
    docs/plan/001-2026-03-12-auth-api/
      plan.md
      01-api-design.md
      02-db-schema.md
      03-error-handling.md
    ```

## 2. 계획 검토

수립한 계획이 적절한지 검토한다.
- 요구사항을 빠뜨리지 않았는지 확인한다
- 과도한 설계가 아닌지 확인한다
- 더 단순한 접근이 있는지 검토한다
- plan.md의 핵심 요약이 상세 문서들과 일치하는지 확인한다
- 상세 문서 간 내용이 중복되거나 모순되지 않는지 확인한다

## 3. 구현

계획에 따라 코드를 작성한다.
- 개발 분야, 기술, 언어 등의 스킬이 있다면 활용한다
- 변경 범위를 최소화한다
- 테스트를 함께 작성한다
- 한 번에 하나의 관심사만 다룬다

## 4. 구현이 목적에 부합하는지 검토

작성한 코드가 원래 요구사항을 충족하는지 확인한다.
- 요구사항 목록과 구현을 대조한다
- 빠진 기능이 없는지 확인한다
- 요구하지 않은 기능을 추가하지 않았는지 확인한다

## 5. 잠재적 버그, 크리티컬 이슈, 보안 문제 검토

코드의 안전성을 점검한다.
- 경계값, null, 빈 값 처리를 확인한다
- 인증/인가 로직에 빈틈이 없는지 확인한다
- 입력 검증과 에러 핸들링을 검토한다

## 6. 개선 사항에 문제가 없는지 검토

개선한 부분이 새로운 문제를 만들지 않는지 확인한다.
- 기존 동작을 깨뜨리지 않는지 검증한다
- 성능에 부정적 영향이 없는지 확인한다

## 7. 기존 코드와 통합/재사용 가능 여부 검토

프로젝트 내 기존 코드를 활용할 수 있는지 확인한다.
- 이미 존재하는 유틸리티나 헬퍼를 확인한다
- 중복 코드를 작성하지 않았는지 검토한다
- 프로젝트의 기존 패턴과 일관성을 유지하는지 확인한다

## 8. 사이드 이펙트 검토

변경이 다른 부분에 미치는 영향을 확인한다.
- 변경된 함수/모듈을 호출하는 곳을 추적한다
- 공유 상태나 전역 설정에 영향이 없는지 확인한다
- 관련 테스트가 모두 통과하는지 확인한다

## 9. 전체 변경 사항 재검토

모든 변경 파일을 처음부터 다시 검토한다.
- diff를 전체적으로 훑는다
- 불필요한 변경이 섞이지 않았는지 확인한다
- 커밋에 포함되면 안 되는 파일(환경변수, 임시파일)이 없는지 확인한다

## 10. 불필요해진 코드 정리

변경으로 인해 더 이상 사용되지 않는 코드를 제거한다.
- 사용되지 않는 import, 변수, 함수를 삭제한다
- 주석 처리된 코드를 삭제한다
- 빈 파일이나 빈 디렉토리를 정리한다

## 11. 최종 코드 품질 검토

코드가 프로젝트 기준에 부합하는지 확인한다.
- 네이밍이 명확한지 확인한다
- 코드 스타일이 프로젝트 컨벤션과 일치하는지 확인한다
- 린터, 포매터를 실행한다

## 12. 사용자 흐름에서 문제가 없는지 확인

실제 사용 시나리오에서 동작을 검증한다.
- 주요 사용자 흐름을 시뮬레이션한다
- 에러 상황에서의 사용자 경험을 확인한다

## 13. 배포 가능 퀄리티인지 검토

프로덕션에 배포해도 되는 수준인지 최종 판단한다.
- 모든 테스트가 통과하는지 확인한다
- 롤백 계획이 있는지 확인한다
- 변경 사항이 문서화되었는지 확인한다

## 14. 커밋 및 PR 작성

변경 사항을 커밋하고 PR을 생성한다.
- 커밋 메시지를 컨벤션에 맞게 작성한다
- PR은 항상 develop 브랜치를 대상으로 생성한다
- .github/ 에 PR 템플릿이 있으면 이를 활용한다. 없으면 자유롭게 작성한다
- PR 설명에 변경 목적과 테스트 결과를 기술한다
- 리뷰어를 지정한다

## Branch Strategy

| Branch | Purpose |
|--------|---------|
| main | production |
| develop | 개발 통합 |
| feature/* | 기능 개발 |
| fix/* | 버그 수정 |

### Branch Start Rule

모든 개발 작업은 항상 최신 `develop` 브랜치에서 시작한다.

1. `develop` 브랜치로 이동한다.
2. 원격 최신 상태를 가져온다.
3. `develop` 브랜치를 `origin/develop` 기준으로 최신화한다.
4. 그 상태에서 작업 목적에 맞는 `feature/*` 또는 `fix/*` 브랜치를 생성한다.
5. 작업 완료 후 PR은 항상 `develop` 브랜치를 대상으로 생성한다.

예시:

```bash
git switch develop
git fetch origin
git pull --ff-only origin develop
git switch -c feature/example-work
```

## Commit Convention

형식: `type: subject`

type: feat, fix, refactor, docs, test, chore

예시:
- `feat: 사용자 인증 API 추가`
- `fix: 토큰 만료 시 갱신 오류 수정`

## Code Review Checklist

### Backend (Go)

- [ ] Errors wrapped with context (`%w`)
- [ ] No ignored errors
- [ ] No hardcoded secrets
- [ ] Tests pass
- [ ] `go vet` clean

### Client (Flutter)

- [ ] No hardcoded secrets
- [ ] Tests pass
- [ ] `flutter analyze` clean
- [ ] Responsive layout (desktop + mobile)

## Development Log

작업 완료 후 개발 일지를 작성한다.
파일 위치: docs/develop/daily/{YYYY-MM-DD}-{개발한 내용 요약}.md
